---
title: "Put an agent into maintenance from another agent"
description: "A worked example for a supervising agent."
---

A supervising agent that is about to restart or upgrade another agent should say so first. The other agent's alerts are then held back and the time is left out of its uptime.

You need an [API key](/guides/api-keys) with the maintenance permission, made by someone who may run maintenance on the agent: one of its operators, or an owner or admin of the organization. A key made by anyone else answers 403 for that agent.

## 1. Find the agent

```sh
curl -H "Authorization: Bearer $BEACONCLAW_API_KEY" \
  https://api.beaconclaw.ai/v1/orgs/ORG_ID/agents
```

Each agent in the answer has an `id`, a `name` and a `status`.

## 2. Start maintenance

```sh
curl -X POST \
  -H "Authorization: Bearer $BEACONCLAW_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"reason":"Runtime upgrade","minutes":30}' \
  https://api.beaconclaw.ai/v1/orgs/ORG_ID/agents/AGENT_ID/maintenance
```

`minutes` defaults to 60. Starting again while a window is in force keeps the one window, made longer if the new request runs later.

## 3. Do the work

## 4. End maintenance

```sh
curl -X DELETE \
  -H "Authorization: Bearer $BEACONCLAW_API_KEY" \
  https://api.beaconclaw.ai/v1/orgs/ORG_ID/agents/AGENT_ID/maintenance
```

If the work overruns and this is never called, the window ends by itself at the time given, and alerts resume.

## See whether an agent is in maintenance

While a window is in force, the agent carries a `maintenance` field wherever the API returns it, with when the window ends and the reason. Otherwise the field is `null`.

```json
"maintenance": { "endsAt": "2026-11-11T18:00:00.000Z", "reason": "Runtime upgrade" }
```

A key that sees only the agent's directory entry gets the end time, with `reason` set to `null`.

## On the machine itself

When the work is done from the agent's own machine, the CLI can do the same with the agent's own token and no API key. See [Maintenance](/cli/maintenance).
